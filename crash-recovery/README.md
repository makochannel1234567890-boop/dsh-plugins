# dsh-crash-recovery — DSH の予期しない終了から自動で復旧する

DSH（DeepSeek Harness）が**落ちたあと**の復旧を自動化する Host プラグインです。
死活ジャーナルを残し、復旧を監督するセッションを**1つだけ**立て、最後に停止した全セッションを
**役割別のプロンプト**で再開します。

> **なぜ作ったか（この PC で実測した事象）**
> PC を直接操作するプラグイン（`desktop_*` / `power_action` など）が範囲の広すぎる操作をして
> DSH ごと落ちることがありました。落ちた瞬間に全ターンが消えるだけでなく、`C:\UE` を
> ワークスペースにする**2つのセッションが数時間止まったまま戻らない**状態が実際に起きました。
> 片方は fanout の**呼び出し元**（`stopped` のランを3本抱えていた）、もう片方は失敗したランの
> **ワーカー**（task t2 / attempt t2-a1-92b9）でした。ここで分かったのが
> **「単なる `resume`（＝『続きをやってください』）では戻らない」**という事実です。
> ワーカーは自分のブリーフを失っており、呼び出し元は自分が何本のランを抱えていたか知らず、
> どちらも直前のツール呼び出しがタイムアウトしたまま残っていました。復旧には
> *ラン・タスク・attempt を名指しで与え直す*必要があります。この挙動が本プラグインの設計理由です。

## 動作（3段階）

1. **死活ジャーナル** — `~/.dsh/storages/crash-recovery/live.json` に bootId / pid / 再起動コマンド /
   実行中セッション / 実行中 fanout ラン / 危険ツールを撃ったセッションを 15 秒ごとに記録。
   正常終了（プラグインのアンロード、`process.on('exit')`）では `clean: true` を書きます。
2. **異常終了の判定** — 次の起動時に前回ジャーナルが `clean: false` なら、
   「終了フックが一度も走らなかった」＝クラッシュと判定。プロファイル違い・古すぎる記録は無視。
3. **監督＋一斉再開** — 危険ツールを撃ったセッションか実行中セッションがあった場合だけ、
   `sessionController.create` で**新規セッションを1つ**作り、修復の指示（`fanout_status` で状態確認 →
   孤児タスクは `fanout_control retry` → 復旧レポートを書く）を与えます。そのセッションが終わったら、
   停止していた全セッションへ**役割別プロンプト**を送り、`sessionController.list` で
   実際に `running` になったかを検証します。

## 役割別プロンプト（ここが肝）

| 種類 | 送る内容 |
|---|---|
| `fanout-worker` | run / task / attempt を名指し。結果が残っていれば**やり直さない**。`fanout_control` は使わない |
| `fanout-review` | run と results/ を示し、判定と根拠だけ。コード変更はしない |
| `fanout-integrator` | 実行済み検証と未実行検証を切り分け、コマンドと終了コードの表を書かせる |
| `fanout-caller` | 自分が開始したラン一覧と状態。`fanout_status` → 必要なら `resume`/`retry`。**`fanout_start` は禁止** |
| `plain` | 作業ディレクトリの現物を読んでから、未完了の分だけ続ける |

全プロンプト共通で「**直前のツール呼び出しをそのまま撃ち直さない**」「進捗を `share_progress` に残す」
「復旧で作業範囲を広げない」を明記しています。

## 停止セッションの見つけ方（4系統の和集合）

再開対象は次の和集合です（重複は除去）。

1. 前回ジャーナルの実行中セッション
2. 前回ジャーナルの危険ツール実行セッション
3. `session-bus` の停止記録 `control.json`（`sessionIds`）
4. `session-bus-control` の停止記録 `control-run.json`（`stopped[].sessionId`）
5. さらに、**`stopped` / `failed` / `escalated` な fanout ランに属するセッション**
   （＝停止記録に載らない「fanout 使用セッション」。上の2つの UE セッションがまさにこれ）
   ただし `state` が `settled` / `cancelled` のワーカー・レビュアーは除きます（すでに結果を出して
   終わった attempt を再プロンプトしても、死んだランは完了しません）。呼び出し元は常に残します。

`running: true` のセッション、サブエージェント、除外指定はスキップし、理由を返します。

> **停止記録の鮮度チェック（2026-11-19 追加）**
> この PC の `control-run.json` は **3日前（2026-11-16 22:24）** の記録なのに 11 セッションを
> 挙げたままで、起動のたびにその 11 件が再開対象になっていました。停止記録は「その直後の再起動」に
> ついての情報なので、`maxRunAgeMs`（既定12時間）より古い記録は無視し、タイムスタンプの無い記録も
> 対象外にしました。

## 一斉再開がホストを落とす問題（2026-11-19 に修正）

この PC で、クラッシュ復旧のたびに **20 セッションを一斉に再開**した結果、DSH の Host が
**V8 ヒープ上限 4 GiB に到達して 4 分おきに 3 回連続で OOM 終了**しました
（22:33 / 22:37 / 22:42、クラッシュログは `exit 134`、`recoveries.jsonl` には毎回
`requested: 20` の resume が残っています）。復旧処理そのものがクラッシュを再生産する
ループになっていたわけです。

再発防止として、再開スイープに次の安全装置を入れました（既定値は `cordis.patch.yml`）。

| 安全装置 | 既定 | 動作 |
|---|---|---|
| `maxSessionsPerSweep` | `3` | 1回の再開は最大3セッション（旧: 20） |
| `resumeGapMs` | `8000` | プロンプト間に8秒待ち、ヒープの急騰を防ぐ |
| `resumeCooldownMs` | `1800000` | **直近30分に resume 済みのセッションは自動では再開しない**（クラッシュ直後の再送でループ化するのを断つ）。`sessionIds` を明示した手動再開は対象外 |
| `resumeMemoryGuardRatio` | `0.75` | V8 ヒープ上限の75%に達したらスイープを中止し、残りを `deferred: memory-pressure` として報告 |
| `maxRunAgeMs` | `43200000` | 12時間より古いランは自動再開の対象外（旧: ジャーナルと同じ7日） |

これにより「再開 → 数分でOOM → 再起動 → また同じ20件を再開」というループは、
**同じセッションを直後に二度再開しない**という一点でも止まるようになっています。

## インストール

```
plugin_manager install_bundle  target: <このフォルダの絶対パス>
```

`application: applied` なら即時反映。`restart-required` なら DSH を再起動してください。

> **Host コードを書き換えた場合は再読込が必要です。**
> 実行中のモジュールは ESM キャッシュに残るため、`plugin_manager set_plugin enabled:false` →
> `enabled:true`（entryId は `include:crash-recovery`）で新しい世代を読み込ませます。

## ツール

| ツール | 説明 |
|---|---|
| `crash_recovery_status` | 前回起動の判定、ジャーナル、両方の停止記録、fanout の状態、実行される再開プランを返す |
| `crash_recovery_resume` | そのプランを実行。**既定は dry-run**（`dryRun:false` で送信）。送信後 4 秒で実際に `running` か検証 |

`crash_recovery_resume` は `sessionIds` を明示すると、そのセッションだけを対象にできます。

## 外部ウォッチドッグ（DSH 自体の自動再起動）

落ちたプロセスは自分を起動し直せないため、プロセス外に見張りを置く場合の同梱スクリプトです。

```powershell
# 何が起きるかだけ確認（実行しない）
node bin\watchdog.mjs --dry-run --once

# 10 秒ごとに見張る（常駐）
node bin\watchdog.mjs --interval 10000 --quiet
```

**2026-11-20 に直した2点（重要）**

1. **正常終了では再起動しない。** この Desktop アプリは終了時に Host を強制終了するため、
   ジャーナルは正常終了でも `clean: false` になります。そのままでは「閉じるたびに勝手に
   開き直す」監視になってしまうので、**Desktop が `crash-*-host.log` を書いたときだけ**
   再起動するようにしました（`--crash-log-dir`、既定 `%APPDATA%\@deepseek-ai\dsh-desktop\logs`）。
   正常終了では renderer のログしか出ないため、区別できます。
2. **Desktop アプリはウィンドウ付きで起動し直す。** ジャーナルの `argv` は Host の起動コマンド
   なので、そのまま再生するとウィンドウの無い Host が起動してしまいます。Electron シェル
   （`DeepSeek Harness.exe`）かつ argv が `-desktop-host` を指す場合は、**実行ファイルだけ**を
   起動してアプリを開き直します。

- ジャーナルの `clean` が `false`、記録された pid が消滅、heartbeat が `--stale`（既定120秒）より
  古い、**かつ Host のクラッシュログが新しい**ときだけ再起動します。
- **暴走しないための上限**: 同じクラッシュ ID につき `--max-relaunch`（既定1）回、かつ
  `--cooldown`（既定1時間）内に同数まで。
- `--interval` の常駐モードは「何もすることがない」「正常終了」でも**止まりません**（次のクラッシュを
  見張り続けるため）。`--once` は1回だけ判定して終了します。

### この PC での有効化（2026-11-20 実施済み）

```
起動フォルダ: %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\dsh-crash-recovery-watchdog.vbs
実行体      : %USERPROFILE%\.dsh\storages\crash-recovery\watchdog-task.vbs
```

ログオン時に VBS が非表示で `node bin\watchdog.mjs --interval 10000 --quiet` を起動します。
タスクスケジューラは権限不足で登録できなかったため、スタートアップ方式にしています。

止めたいときは `Get-CimInstance Win32_Process -Filter "Name='node.exe'"` で
`watchdog.mjs` の PID を探して停止し、上記2つの .vbs を削除してください。

## 自動再開の対象（2026-11-20 にさらに限定）

再開スイープは **「その終了で何かが中断された」証拠があるときだけ** 自動で動きます。

- 起点になるのは「前回ジャーナルの実行中セッション」「危険ツール実行セッション」
  「鮮度のある停止記録」だけです。
- 未完了ランに属するセッションは、上記のどれかが存在するときだけ**補助候補**として加わります。
- したがって、何も動いていなかった通常の再起動（この PC では終了が常に `clean: false` に
  見える）では、**古いランのセッションは復旧しません**。
  （2026-11-20 07:27 の再起動で古い fanout 呼び出し元3件が復旧した事象の修正）

## 制限（正直なところ）

- **落ちたプロセスは自分を復旧できません。** プロセス内の復旧は「次に DSH を起動したとき」に走ります。
  起動まで無人にしたい場合だけ、上の外部ウォッチドッグが必要です。
- 外部ウォッチドッグは `process.execPath` + `argv` の再生で再起動します（Electron アプリでは
  ヒューリスティック）。`--dry-run` で必ずコマンドを確認してから使ってください。
- 二重起動は防げません。ユーザーが手で開いた場合と競合し得るため、再起動回数は意図的に絞っています。
- 監督セッションは「1クラッシュにつき1つ」を `wx`（排他作成）のクレームファイルで保証しますが、
  プロファイルを跨いだ重複までは面倒を見ません（ジャーナルはプロファイル単位）。
- クラッシュ**原因**の修正はしません。復旧と記録だけです。
- `crash_recovery_*` が `lossless JSON` エラーになる場合は、ツール出力に `undefined` が混ざっています
  （このバージョンでは正規化済み）。

| 項目 | 結果 |
|---|---|
| `node --test`（detect / resume-plan / journal / prompts / watchdog） | **50 件すべて pass** |

| 構文チェック（`node --check`、全 .js/.mjs） | pass |
| プラグイン導入（`install_bundle`） | `application: applied`、ツール2つが公開 |

| 監督セッションの単一性（`wx` クレームの競合） | テストで確認 |
| 停止記録の2系統＋fanout 未完了ランからの対象合成 | テストで確認 |
| **実セッションでの復旧テスト** | 停止していた `C:\UE` の2セッション（fanout 呼び出し元 `session-4f68a0b0…` と ワーカー `session-2bcfa281…`）に対し、役割別プロンプトを送信 → 送信4秒後の `sessionController.list` で**両方 `running: true`** を確認。`failed: []`、`skipped: []` |

未確認: 実際に DSH をクラッシュさせての監督セッション起動（`kill` による実測）は行っていません。

「クラッシュ→次回起動→監督→一斉再開」の通しは次回の実クラッシュ時に検証されます。
