# dsh-fanout — 1セッションをNセッションに開き、最後に自動で統合・検証する

DeepSeek Harness 用のプラグインです。**1つの依頼**で、大きく重さの違う複数の仕事を
渡すと、プラグインが自分で分岐セッションを起動し、仕事を重さで振り分け、終わったら
**統合用のセッションを自動で立ち上げ**、結果の突き合わせ・e2e検証・ビルドまで済ませて
依頼元のセッションに短い報告を返します。

さらに、モデルが制約に押されて「選択肢を広げるのを無意識に省く」現象を打ち消す
**展開ゲート**と、トークン量を目で調整できる **2本のスライダー**（Web UI）を備えます。

## 使い方（モデルから）

```
fanout_start(
  objective: "決済APIの v2 移行。影響範囲は3つ。",
  tasks: [
    { title: "サーバ実装", brief: "<自己完結した指示。触るファイル、受け入れ条件>", weight: 5 },
    { title: "SDK更新",   brief: "<...>", weight: 2, scope: ["packages/sdk"] },
    { title: "移行ガイド", brief: "<...>", weight: 1 },
  ],
  workers: 3,              // 分岐セッション数（スライダー）
  expansion: 60,           // 思考拡張（スライダー。統合時の探索量と見積りに反映）
  verify: ["pnpm test", "pnpm build"],
)
```

- 仕事は `weight` の大きい順に、最も空いているワーカーへ詰められます（LPT）。
  重い仕事1つ＋軽い仕事3つ、のような非対称な束でも偏りません。
- ワーカーには **目的1段落＋自分の仕事＋結果ファイルの置き場所** だけが渡ります。
  親会話も、他のワーカーの会話も渡りません。
- 全ワーカーが落ち着くと、**統合セッションが自動で起動**し、
  `results/worker-*.md` と実物を突き合わせ、`verify` のコマンドを実行して
  `final.md` を書きます。コマンドと終了コードは表として残ります。
- 終わると依頼元セッションに `<fanout_result>` として短い要約が届きます。

進捗: `fanout_status` / 中断: `fanout_stop`。

## 使い方（Web UI から）

コンポーザの上に **Fan-out チェックボックス** が出ます。

- チェックを入れると、その場で**モーフィング展開**して設定が開きます。
- **割り当て: 自動（既定）** — 親セッション（いまのセッション）が分岐セッション数と
  思考拡張を自分で決めます。必要量＋余分（最広レイヤー + 1、深さに応じた探索軸 + 余白）で
  決めるので、安い既定値へは縮退しません。
- **割り当て: 手動** — 2つのスライダーをそのまま使います。
  - **分岐セッション数**（1〜8）: 起動するワーカーの数。
  - **思考拡張**（0〜100）: 0=オフ / 1–30=1軸 / 31–60=3軸 / 61–85=5軸+分類ゲート / 86–100=8軸+分類ゲート。
- 目的・タスク（1行1件 `title :: brief :: weight`）・検証コマンドは展開パネルで書けます。
  タスク欄が空のまま「開始」すると、プラグインは**いまのセッションに分解依頼**を出し、
  モデルが目的を非対称な仕事に分けて `fanout_start` を呼びます。
- チェックは **1回きり**。run が始まると自動で外れ、次の指示には持ち越しません。
- 状態行に、稼働中 run・settled/total・推定トークンが出ます。

### fan-out が負ける指示は、自動で単一セッション

このプラグインは「広く深い」指示のためのもので、並列化の汎用スイッチではありません。
次に当てはまるときは Host が `fanout_start` を **単一セッションへ差し戻します**
（`ok:false` / `single_session:true` と理由を返します）。

| 条件 | なぜ負けるか |
|---|---|
| 仕事が3本未満 | 並列に走るものがなく、レビュー1回分だけ高くつく |
| 純粋な連鎖（幅が1） | どの層も同時に2本走らない |
| ブリーフ合計が600字未満 | セッション固定費が作業本体を上回る |

差し戻されたら、**そのセッションで普通に作業して報告する**のが正解です。どうしても
オーケストレーションしたいときだけ `force: true` を明示します。

スライダー値は `~/.dsh/storages/fanout/config.json` に保存され、次回も残ります。
UI とツールは同じエンジンを叩きます（操作の実装は1つだけ）。

## 進捗ボード（左サイドバー）

左サイドバーのアイコン列に **Fan-out** が加わります（`sidebar.panellist` の id
`fanout`、順序 30）。クリックすると中央カラムに進捗ボードが開き、分割したチームが
いまどこまで来たのかが1画面で分かります。

- **上段**: 実行中の本数 / ワーカーの完了数（settled/total）/ 統合中の本数
- **run ごとのカード**（新しい順、最大8件）
  - `run_id` の短縮表示・状態ピル・進捗%・経過時間
  - 目的（1行。ホバーで全文）
  - 進捗バー（`role="progressbar"` と `aria-valuenow` 付き）
  - 段階ストリップ: `分岐実行 › 統合 › 完了`
  - ワーカーチップ `W1 実行中 3件`（ホバーで担当中のタスク名）
  - 統合の状態と、あれば `final.md` のパス
- 色は `--dsw-alias-*` のテーマトークンだけ。ライト/ダーク双方で成立します。

進捗率の定義は1箇所だけ（`lib/plan.js` の `progressOf`）:
**ワーカーの完了で85%、統合で残り15%**。全ワーカーが落ち着いた時点で下限90。
`completed` は100、`failed` / `stopped` は実際に到達したワーカー分だけを返します。
「5本終わったのに92%で止まって見える」「止めたのに100%」は起きません。

ボードは2秒ごとに自分で `/state` を読みます。コンポーザのバーを折りたたんでいても
更新は止まりません。

> **Host 半の再読み込みについて**: `percent` / `phase` / `worker_details` /
> `created_at` を返すのは Host 側（`engine.uiRun()`）です。Host 半は Harness の
> 再起動で読み込まれるので、導入直後は旧 Host のデータ（`total` / `settled` /
> `status` のみ）になります。ボードはその場合も同じ数字を自前で導出して表示し、
> **ワーカーチップだけを出しません**（無い情報を作らないため）。Harness を
> 再起動すると、各ワーカーの状態とタスク名まで出ます。

## 展開ゲート（思考の省略を打ち消す仕組み）

`divergence_check(objective, proposal, constraints?, intensity?)` を呼ぶと：

1. **あなたの提案を見せない** 新しい探査セッションを、直交するレンズごとに1本ずつ起動します
   （制約の反転 / 目的の再定義 / 失敗先行 / ズーム / 利害関係者の交代 / 既存解の流用 /
   削除テスト / 非対称な機会）。
2. 各探査は `OPTION:` 行で候補を2〜4個返します。提案を見ていないので、あなたの
   狭め方に引きずられません。
3. ツールは候補を `a1, a2, …` として返し、**ゲートは閉じたまま**です。
   同じ `divergence_check` に `divergence_id` と、**全候補**への
   `adopt / reject / defer + 理由` を付けて再び呼ぶまで閉じています。
4. 分類は `~/.dsh/storages/fanout/divergence/<id>.json` に残ります。後から
   「何を捨てたか」を検証できます。

要点は「発想を増やす」ことではなく、**捨てた選択肢を記録させ、捨てる判断を
見える化する**ことです。トークンを使いすぎないよう、軸の数はスライダーで絞れます。

## インストールと有効化

```
plugin_manager install_bundle  target: <このディレクトリの絶対パス>
plugin_manager set_bundle      target: "dsh-fanout"  enabled: true
```

有効化するとツール群（`fanout_start` / `fanout_approve` / `fanout_control` /
`fanout_status` / `fanout_stop` / `divergence_check`）と、コンポーザ上の
**Fan-out チェックボックス**が現れます。UI は `127.0.0.1:51337` か同一オリジンの
`/fanout-api` に接続します。

> **このプロファイルでは正式に有効化済み**です（`set_bundle` → `application: applied`、
> ツールがエージェントに公開されていることを実測）。以前の README にあった
> 「HMR が詰まって `enabled: false` のまま」という状態は、Harness 再起動で解消しました。
> もし別プロファイルへ入れる場合は、上記 2 コマンドを順に実行してください。

### 検証コマンド

```powershell
node test/run-all.mjs        # 13ファイル（arm / plan / prompts / bridge / graph / queue / gates / context / kernel / prompts2 / apply / ui-state / ui-panel）
node --check index.js
node --check client.js
```

`arm.test.mjs` は適性ゲートと自動予算（レベルの幅・深さ、3つの拒否条件、上限クランプ）を、
`ui-state.test.mjs` は `FanoutEngine` の prototype を直接呼んで `/state` に載る形を固定します。
`ui-panel.test.mjs` は `client.js` を ModuleLoader factory として読み、React の代役を
与えて**実際にパネルとドックを描画**します（DOM もブラウザも不要）。サイドバー行と
`main` パネルが同じ id で登録されること、進捗バーの `aria-valuenow` が 0–100 に収まること、
旧 Host のデータでも落ちないこと、そして**コンポーザのチェックボックスと折りたたみ状態の
モーフ容器が実際に出る**ことを見ます。

## 状態とファイル

```
~/.dsh/storages/fanout/
  config.json                 # UI スライダーの保存値
  bridge.json                 # 実際に使ったポートとトークン
  runs/<runId>/run.json       # run の状態
  runs/<runId>/results/*.md   # ワーカーの結果ファイル
  runs/<runId>/final.md       # 統合レポート
  divergence/<id>.json        # 展開ゲートの候補と分類
```
ワークスペース側にも `.dsh-fanout/runs/<runId>/` ができます（ワーカーが結果を書く場所）:
`objective.md`（全文）、`manifest.md` / `manifest.json`（成果物の索引: path・bytes・sha256・
共有プレフィックスのハッシュ）、`prompts/<attempt>.md`（実際に渡したブリーフ）、
`results/<attempt>.md`、`final.md`。

## 仕組みと制約

- セッション生成は `sessionController.create` → `prompt`。通常のセッションなので
  サイドバーに現れ、人間が中を覗けます。
- 完了検知は `api-session/status` と `session/event`（`turn/end`）。巡回ポーリングは
  せず、締切 watchdog だけが15秒ごとに動きます。
- セッションログに新しいイベント種別は書きません。状態はすべて上記のファイルです。
- **プロセス内メモリの駆動部は再起動で失われます**。run.json / final.md は残るので、
  何がどこまで進んだかは後から読めます。
- UI バーは `127.0.0.1` のみにバインドし、`x-fanout-token`（起動ごとに生成）で守ります。
  `/health` だけがトークンを返します（ループバック限定）。
- 人間の承認が要る操作を代行するものではありません。ワーカーは通常の権限で動きます。

## 設計メモ

- 文脈の節約は「渡さない」ことで実現しています。ワーカーは親会話を持たず、統合は
  ワーカーの全文ではなく 1200 字の要約だけを受け取ります。
- 重さの非対称は LPT パッキングで吸収します（`lib/plan.js`）。
- 展開ゲートの強さは「提案を見せない」ことと「全候補の分類を強制する」ことの2点だけ。
  余計なプロンプトの修辞には頼りません。

## v2: 監視付きタスクグラフ（2026-11-17）

index.js は lib/kernel.js を積むようになりました。v1 の「平らな束を並列実行」は
「**依存関係つきのタスクグラフ**」に置き換わり、次のことがコードで強制されます。

- `tasks[].dependsOn` による DAG（循環・不明な依存は spawn 前に拒否）
- `kind: implementation|verification|requirements` は `acceptance` と `verify` が必須
- 各タスクの完了後に**独立レビュアー**が走り、`VERDICT:` / `ACCEPT:` / `FINDING:` 行を
  パースして合否を決める。不合格なら**修復タスク**を自動で差し込み、次のラウンドへ。
  上限に達したら run は escalated で止まる（黙って通さない）
- 全結果は attempt トークン付き。古い試行の回答は受理しない（規定違反は1回だけ再試行）
- 統合レポートは節と「コマンド / 終了コード」表を検証。不合格なら1回だけ書き直させる
- `fanout_approve`（承認前は spawn しない `approval:"required"`）と
  `fanout_control`（pause / resume / retry / steer / edit / takeover）
- **再起動・リロード後も復帰**する: run.json から in-flight の run を引き継ぎ、
  セッションを再追跡する（v1 の run.json も移行して引き継ぐ）

## v2.1: コンテキスト予算とファイル化

トークン費用の主因は「同じ objective と契約を全セッションに貼り直すこと」でした。次の
プロセスを追加しています。

- 全ブリーフが同じ**共有プレフィックス**（`lib/context.js` の `SESSION_RULES` + run facts）
  から始まる。ハッシュは `manifest.json` の `prefix.sha256` に記録され、契約変更＝意図した
  キャッシュミスとして見える
- objective は先頭600字だけ各ブリーフに載せ、全文は `objective.md` に置く
- レビュアーは生の結果スライスではなく構造化ダイジェスト（summary / changed / verified /
  open / findings）を受け取る
- 統合は「タスク1行のマニフェスト表」だけを受け取り、必要なら結果ファイルを読む
- 各ブリーフを `prompts/<attempt>.md` に保存し、結果・最終レポートを `manifest.json` に
  path + bytes + sha256 で索引化（**ファイリングとマニフェスト**）
- 同一 objective・同一ワークスペースの**重複ランを既定で拒否**（`allowDuplicate: true` で
  上書き）。同一目的の4重起動が実際に起き、レビューと統合の費用を4倍化していました
- 再試行時は「前回どこで落ちたか」をブリーフに添える（marker / VERDICT 抜けの盲目的な
  再試行を防ぐ）

固定フィクスチャでの実測（文字数、before → after）:

| フィクスチャ | task | review | integrator | 合計 |
|---|---|---|---|---|
| 6タスク・基準1件・brief 1200字 | 3906 → 4370 | 3946 → 3402 | 9474 → 3374 | 56586 → 50006 |
| 24タスク・基準12件×300字 | 10541 → 8999 | 8776 → 7231 | 33289 → 4395 | 496897 → 394170 |

task ブリーフは小さいフィクスチャでは微増します（固定プレフィックスを各セッションが1回
払うため）。代わりにプレフィックスは run 内の全セッションで同一＝キャッシュヒットし、
統合はダイジェスト爆撃を受け取らなくなりました。詳細は DESIGN-V2.md。

v2.1 は UI の**データ契約**を変えていません（Host は既存のドックが読む形 —
percent / phase / worker_details など — をそのまま返します）。UI 自体を作り替えたのは
v2.2 です。詳細な契約は DESIGN-V2.md。

## v2.2: コンポーザのチェックボックスと単一セッション自動判定（2026-11-18）

入力ドックを「常に開いた設定フォーム」から「**1つのチェックボックスがモーフィングで
開く**要素」へ作り替え、分割するかどうかの判断を親セッションへ寄せました。

### 見た目

- 閉: `☑ Fan-out` の1行。未チェック時は「チェックすると、この指示を親セッションが
  分割実行します」を添えます。
- 開: 同じ行の下に `自動（親が決定）` / `手動` の切替、説明、手動時の2スライダー、
  目的・タスク・検証コマンド欄が展開します。
- モーフは `grid-template-rows: 0fr → 1fr` で**実コンテンツ高さ**まで伸ばします
  （`max-height` の当て推量ではない）。不透明度・枠線・背景も同時に遷移。
  閉状態は `visibility: hidden` を遅延付きで当てるので、中身はタブ順にも入りません。

### 状態は Host が持つ

- `POST /arm` — `{session_id, armed, mode, workers?, expansion?}`。チェックは
  **1回きり**で、arm したセッションの次の `fanout_start` が消費します。1時間で失効。
  ワーカーセッションには一切漏れません。
- `GET /state?session_id=<id>` — そのセッションの `armed` を返します。セッション名が
  無い要求には `{armed:false, mode:"auto"}` を返すので、ドックは推測せず「オフ」を描きます。

### 適性ゲート（`lib/arm.js`）

armed 経路の `fanout_start`（＝コンポーザから arm されたセッションの実行）だけが
適性判定を通ります。直接呼び出しは従来通りで、後方互換です。

| 条件 | 判定の根拠 |
|---|---|
| タスクが3本未満 | 並列に走るものがなく、レビュー1回分だけ高い |
| 幅が1（純粋な連鎖） | どの層も同時に2本走らない |
| ブリーフ合計 600字未満 | セッション固定費が作業本体を上回る |

拒否時は `ok:false` / `single_session:true` / `reasons[]` / `metrics{}` / `guidance` を返し、
「このセッションで自分でやって報告しろ、`force:true` で無理押しするな」と伝えます。

### 自動予算

同じ `lib/arm.js` が2つのダイヤルを決めます。**必要量＋余分**が既定です。

```
workers   = min(maxWorkers,   最広レイヤー + 1)      # 空きスロットを遊ばせない
expansion = min(maxExpansion, 60 + 8 * (深さ - 1) + 15)
```

大きい指定はそのまま通り、小さい指定は下限まで切り上げます。`手動` はユーザーの値を
そのまま使います（ゲート自体は手動でも効きます — 連鎖に fan-out を強制したいときだけ
`force:true`）。決定は run の `budget{workers, expansion, source, note}` に残り、
`fanout_start` の戻り値にも `budget` / `workers_concurrency` / `expansion` として出ます。

### なぜ UI ではなく親セッションが決めるのか

プロンプトは「作業がどう分解されるか」を書いていません。Host は objective の意図を
見られません。**依頼文と、いま組んだグラフの両方を持つのは親セッションだけ**です。
そこでプロンプト節は「決めた本数を1行で宣言してから `fanout_start` を呼べ」と指示し、
`objectiveFit`（箇条書き・長さからの粗いヒント）はパネルの事前警告にだけ使い、
**ゲートには使いません**。

## v2.3: コンポーザ乗っ取り・モデル固定・3階層ネスト（2026-11-20）

チェックボックスはそのまま。有効にすると**入力窓がファンアウト面に置き換わります**。

### 何が変わるか

| 対象 | 変更 |
|---|---|
| 入力窓 | チェック中は `conversation.input.overlay` のパネルがカード全面を覆い、下の入力は透明になる。`grid-template-rows: 0fr → 1fr` + `opacity` で 260ms モーフ（`prefers` ではなく `transition` のみ）。「入力に戻す」で即座に解除（楽観更新 + Host の次回ポーリングで確定） |
| モデル | 実行で作るセッションと、チェックを入れたセッションを **v4.1 flash / max effort** に切り替え。id は固定せず `sessionController.modelCatalog()` から `modelPattern`（既定 `4\.1[\s._-]*flash`）で解決。見つからなければ flash 系へフォールバックし、それでも無ければ継承モデルのまま（実行は止めない）。`/state` の `model_label` に解決結果が出る |
| サイドバー | 実行に属するセッション行の先頭 16px セル（`sidebar.session.row.leading`）にファンアウトのアイコン。親は「ファンアウトの親セッション」、ワーカーは「ワーカーセッション」 |
| 単一の親 | プロンプト節に「作業ディレクトリの実行を `fanout_status` で確認し、目的か書き込み範囲が重なるなら `fanout_enqueue` / `fanout_control steer` で既存実行を延長、重ならなければ新規」という調停ルールを追加 |
| ネスト | `run.depth` を記録し、**root → child → grandchild の3階層**まで。4階層目は `depth_refused: true` で拒否（`maxDepth`、既定3） |

### 安全性のための線引き

- パネルは**スロットの親が positioned のときだけ絶対配置**。`static` ならカード内フローに
  フォールバックするので、レイアウト変更で会話全体を覆う事故が起きない。
- グローバル CSS も `document.body` への書き込みもなし。テーマトークンのみ。
- モデル切替は失敗しても例外を投げない（`applySelection` が `{ ok:false }` を返し、実行は継続）。
  まず effort 付き、拒否されたら effort を落として再試行。
